## 1. Claude Code 2.1.232: форк-режим по умолчанию и @-упоминание сессий

**Что нового.** Версия 2.1.232 от 13 августа 2026. Два ключевых изменения: (1) **Форк-режим по умолчанию** — субагенты запускаются с полным наследованием диалога и prompt cache без ручной настройки; (2) **@-упоминания сессий** — введите @имя в промпт, SendMessage доставит его напрямую; каждая интерактивная сессия получает уникальное имя формата "слово-слово". Безопасность: исправлены PowerShell-bypass через запись переменных, Cygwin-symlink bypass на Windows, наследование git-trust вложенными репозиториями. MCP: исправлено зависание соединений при определении версии протокола.

**Зачем вам.** Форк по умолчанию — главная выгода для параллельных агентных сессий: субагент больше не начинает с чистого листа, знает весь контекст родителя и экономит токены на prompt cache. @-упоминания убирают необходимость помнить длинные ID сессии. Исправления безопасности критичны для Windows-пользователей с Cygwin.

**Как попробовать.** Обновите: npm install -g @anthropic-ai/claude-code. Форк: запустите субагента — режим работает автоматически. @-упоминания: в промпте напишите @имя-сессии. Посмотреть имена активных сессий: /listAgents.

## 3. Claude Code 2.1.233: GitLab MR в --worktree, лимит памяти Bash и кэш WebFetch

**Что нового.** Версия 2.1.233 от 14 августа 2026. Новые функции: (1) GitLab MR URL работает с флагом --worktree и в claude agents — как давно работал GitHub PR URL; (2) CLAUDE_CODE_TOOL_MEMORY_LIMIT — opt-in cgroup-лимит памяти для bash-команд на Linux; (3) CLAUDE_CODE_WEBFETCH_CACHE_TTL_MS — TTL кэша WebFetch в миллисекундах; (4) forward_user_identity в apps gateway для трекинга расходов по пользователям. Исправлены: cloud-сессии теряли статус при перезагрузке, MCP v2 бесконечная переподписка, 100% CPU у idle-сессий с sandbox на Linux.

**Зачем вам.** GitLab-команды наконец получили то, что GitHub-пользователи давно имели: автоматическое ветвление и агентное ревью прямо из MR-URL. CLAUDE_CODE_TOOL_MEMORY_LIMIT полезен если агентные bash-команды потребляли слишком много RAM. WEBFETCH_CACHE_TTL — для задач где данные быстро меняются. Фикс 100% CPU снимает проблему idle-сессий на серверах с sandbox.

**Как попробовать.** Обновите: npm install -g @anthropic-ai/claude-code. GitLab worktree: claude --worktree https://gitlab.com/.../merge_requests/123. Лимит памяти: export CLAUDE_CODE_TOOL_MEMORY_LIMIT=512M. WebFetch TTL: export CLAUDE_CODE_WEBFETCH_CACHE_TTL_MS=60000.

## 4. Claude Code 2.1.229: remote-control --continue и SSE keepalive для длинных задач

**Что нового.** Версия 2.1.229 от 12 августа 2026. Новые функции: (1) claude remote-control --continue — документированный флаг возобновления Remote Control сессии; (2) SSE keepalive-пинги во время длинных reasoning-пауз — соединение не рвётся; (3) server-supplied hooks в self-hosted runner; (4) plugin marketplace command sources с перерешением на каждую сессию. Исправлены: длинные ответы пропадали или печатались дважды при стриминге, RangeError на progress bars в узких терминалах, Windows UNC-путь crashes, /model не принимал Sonnet/Opus 1M context для custom gateway.

**Как попробовать.** Обновите: npm install -g @anthropic-ai/claude-code. Возобновление: claude remote-control --continue [session-id]. Остальные исправления работают автоматически после обновления.

## 5. Конференция Just AI (700 участников): бот без LLM — доставляемость 70% -> 95%, поддержка -30 запросов/день

**Бизнес.** Just AI — российская AI-компания (100-200 сотрудников), организатор конференции Conversations с 500-700 участниками дважды в год.

**Процесс.** Рассылка персональных писем каждому участнику: уникальные ссылки на стриминг и ID доступа в мобильное приложение. Данные в нескольких Excel-вкладках, ID назначались вручную через приложение без API.

**Было.** Рутинное время: 2+ ч/день. Пик за 2 дня до события: 8+ ч. Доставляемость: 70% (30% писем не доходили на домены банков, госструктур). Поддержка: 30+ обращений в день "пришлите ссылку". Риски: дубли, пропущенные участники, рассинхрон таблиц.

**Сделали.** Три детерминированных воркфлоу на Just AI Agent Platform (LLM не используется). Excel_Workflow1 — сводит вкладки-источники в мастер-лист. Excel_Workflow2 — определяет незаполненные ID, экспортирует в staging-вкладку, подтягивает возвращённые ID по email, назначает ссылки последовательно из пула. Email Workflow — отправляет HTML-письма через SMTP собственного домена, батчи по 30 с задержкой. Плюс веб-панель для ручного триггера и статус-мониторинга.

**Стало.** Доставляемость: 95%+, подтверждена на доменах банков и госструктур. Спам: <3%. Время/день: 30 мин вместо 8 ч. Поддержка: единицы обращений вместо 30+. Расходы на LLM: 0 руб. Экономия vs event-платформ: 50 000 руб+ за мероприятие.

**Инструменты.** Just AI Agent Platform, Google Sheets (мастер-лист и пул ссылок), SMTP с собственного домена, партнёрская платформа стриминга.

**Как повторить.** 1) Таблица: вкладки-источники участников, мастер-лист, staging-вкладка ID, пул ссылок. 2) Воркфлоу слияния: новые строки из источников -> мастер. 3) Воркфлоу ID: детект пустых -> экспорт -> импорт совпадений -> назначение ссылок. 4) Email-воркфлоу: HTML-шаблон с переменными, SMTP, пакеты по 30 с задержкой. 5) Кнопка ручного запуска и экран статуса.

**Подвох.** Один шаг остаётся ручным: приложение конференции без API — вручную добавить участников и экспортировать ID. Пакет >30 писем триггерит спам-фильтр — нужно тестировать на корпоративных адресах. При сбое SMTP на середине рассылки нужен механизм повторной отправки только непочатым.

## 6. Облачный провайдер OXYGEN: 4 скрипта вместо ручных проверок — инцидент за 5 мин, неделя IOPS -> 20 строк кода

**Бизнес.** OXYGEN — российский облачный IaaS-провайдер, 200-500 сотрудников, 6 регионов (Москва, СПб, Екатеринбург, Люксембург, Казахстан, Узбекистан). Кейс от команды поддержки виртуальной инфраструктуры.

**Процесс.** Четыре повторяющихся процесса: (1) учёт ёмкости ресурсов по всем кластерам; (2) проверка конфигурации новых объектов клиентов; (3) сбор данных об инцидентах (затронутые VM, тексты уведомлений); (4) расчёт лимитов IOPS для дисковых политик.

**Было.** Учёт ёмкости: часы на каждый запрос, исторических данных нет. Проверка конфигурации: ручной обход нескольких типов объектов без единого чеклиста. IOPS-таблицы: ~неделя ручной работы на каждую политику. Инцидент: поиск затронутых VM занимал "драгоценные минуты" до начала устранения.

**Сделали.** (1) Почасовой дашборд метрик по всем кластерам с историей с 2022 года. (2) Версионированный чекер конфигурации — алерт при нарушении стандарта. (3) Telegram-бот как единая точка приёма всех алертов. (4) Детерминированная IOPS-функция: ~20 строк кода, 4 значимых — одинаковый ввод всегда даёт одинаковый результат. (5) Агрегатор инцидентов: автопоиск затронутых VM и подготовка текста уведомления.

**Стало.** Ёмкость: real-time по всем регионам, резерв 20% фиксируется автоматически. Конфигурация: проверка за минуты. Инциденты: список VM за ~5 мин. IOPS: полностью воспроизводимо, неделя ручной работы исключена. Штат поддержки не рос при масштабировании инфраструктуры.

**Инструменты.** VMware vCloud Director API + vCenter API, Zabbix, Telegram Bot (по туториалу с Habr), внутренний дашборд, Python/Bash-скрипты.

**Как повторить.** 1) Выделить операции, повторяющиеся по расписанию с фиксированными правилами. 2) Подключить API платформы (vCenter, AWS, Yandex Cloud). 3) Почасовой сбор метрик с хранением истории. 4) Правила -> версионированный чеклист с алертом при нарушении. 5) Telegram-бот: низкий порог, туториалы открытые. 6) Расчёты: детерминированные функции, один ввод -> один вывод.

**Подвох.** Чеклист проверяет соответствие правилам, но не корректность самого запроса клиента. Правила надо актуализировать при обновлении API и внутренних стандартов. Важно различать "API вернул 0" от "API недоступен" — без явной обработки ошибок будут ложные нули.

## 7. Строительная компания Locke Buildings: AP-автоматизация — 10-12 ч/нед -> 2 ч/нед, сотрудник работает из дома 4 дня

**Бизнес.** Locke Buildings — строительная компания (коммерческие, сельскохозяйственные, жилые здания), 24 сотрудника, США.

**Процесс.** Обработка входящих счетов (AP): печать, физическая маршрутизация на согласование, ручной ввод данных в QuickBooks. 500+ счетов в месяц.

**Было.** 10-12 часов в неделю на AP. Бумажное согласование требовало физического присутствия бухгалтера в офисе каждый день. 500+ счетов вводились вручную построчно.

**Сделали.** Подключили MakersHub для автозахвата и цифровой обработки счетов, интегрированного с QuickBooks. Электронные маршруты согласования без бумаги.

**Стало.** Время AP: 10-12 ч/нед -> ~2 ч/нед. Экономия: 40+ часов/месяц (около $11 400/год по оценке вендора). 500+ счетов/месяц — полностью в цифре. Бухгалтер Трина работает дома 4 дня в неделю: "процесс больше не привязан к принтеру".

**Инструменты.** MakersHub (AP-автоматизация) + QuickBooks.

**Как повторить.** 1) Выбрать AP-платформу с интеграцией в вашу бухсистему (Bill.com, Dext, Rho для QuickBooks; для 1С — искать коннектор отдельно). 2) Настроить электронные маршруты согласования. 3) Перевести вендоров на PDF-счета или настроить захват из почты.

**Подвох.** Кейс опубликован вендором (MakersHub), цифры экономии — расчёт по ставке вендора. MakersHub заточен под строительную и торговую отрасль США; для российских компаний с 1С — другие решения. Интеграция AP с 1С сложнее, чем с QuickBooks.

## 8. Стоматологическая клиника: AI-рецепционист — 47% пропущенных звонков -> 0%, запись +44%

**Бизнес.** Стоматологическая клиника доктора Клэр (имя обезличено), два администратора-рецепциониста. Точный масштаб в источнике не указан.

**Процесс.** Приём входящих звонков и запись на приём: в пиковое время и при занятости администраторов часть звонков оставалась без ответа.

**Было.** 47% входящих звонков уходили без ответа. Потенциальные пациенты не дожидались и обращались в другие клиники.

**Сделали.** Внедрили AI-рецепциониста Octavius AI — интегрировали с practice management системой клиники. 24/7-режим: бот отвечает на звонки, отвечает на типовые вопросы, записывает на приём.

**Стало.** Пропущенные звонки: 47% -> 0%. Запись на приём: +44%. Нагрузка на администраторов снизилась на рутинных звонках.

**Инструменты.** AI-рецепционист Octavius AI, интеграция с practice management software клиники.

**Как повторить.** 1) Выбрать AI-рецепциониста с интеграцией в вашу МИС. 2) Настроить сценарии: запись, перенос, типовые вопросы, передача на живого оператора. 3) Тест 1-2 недели параллельно с администратором. Для РФ: Aimylogic, Voicebot.ru, интеграция с 1С:Медицина или Infoclinica.

**Подвох.** Кейс опубликован вендором (Octavius AI), независимой верификации нет. Атрибуция только по имени "доктор Клэр" без названия клиники — анонимный кейс. Интеграция с российскими МИС-системами требует отдельного поиска совместимых решений.
